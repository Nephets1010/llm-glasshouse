# ADR-0005：为什么首版仍锁在 Spring Boot 3.5

- **状态**：已接受（2026-10-10）
- **相关**：架构文档 §2（模块与依赖方向）、§8.2（core 零框架依赖）
- **决策者**：Kou（llm-glasshouse 负责人）

## 背景

Spring Boot 3.5 的**开源支持已于 2026-06-30 结束**（最后开源版本 3.5.16，发布于 2026-06-25）。
同一天结束的还有 Spring Framework 6.2、Spring Security 6.5、Spring Cloud 2025.0。

3.5 是 3.x 线的最后一个版本，**没有 3.6 可以停留**，所以「再等等 3.x 的下一个 patch」这条路不存在。
当前在 OSS 侧能选的是 4.0（OSS 支持至 2026-12-31）与 4.1（至 2027-07-31）。

本文档要回答的是：**本项目首版为什么没有直接上 4.x，以及这个选择的风险边界在哪里。**

## 事实基线

| 事实 | 值 | 来源 |
|---|---|---|
| Boot 3.5 发布日期 | 2025-05-31 | Spring 官方发布列车 |
| Boot 3.5 OSS 支持结束 | **2026-06-30** | Spring 生命周期页面 |
| Boot 3.5 最后 OSS 版本 | 3.5.16（2026-06-25） | Maven Central |
| Boot 3.5 **商业支持**结束 | **2032-06-30** | Tanzu Spring（付费） |
| Boot 4.0 / 4.1 | OSS 至 2026-12-31 / 2027-07-31 | Spring 官方 |
| 本项目锁定版本 | `3.5.16`（精确，非 `3.5.x`） | `pom.xml` |

## 决策

**首版锁在 Boot 3.5.16，接受 OSS 支持已结束的事实。**

理由按权重排序：

1. **可用的时间窗极小**。Boot 4.0 的 OSS 支持也只到 2026-12-31（不足 3 个月），
   4.1 到 2027-07-31。选一个「刚发布半年、还没被广泛验证」的版本作为首版基线，
   比选一个「已稳定两年、只是 OSS 停了」的版本风险更大。

2. **Spring AI 生态当前以 3.x 为主**。本项目 starter 直接依赖 Spring AI 的 `ChatModel`
   抽象。Spring AI 各版本的 3.x/4.x 兼容矩阵仍在演进中，此时跨大版本迁移等于
   同时承担 Spring Boot 与 Spring AI 两条升级线的风险。

3. **迁移成本在本项目里已被结构性锁死**（见下节），因此「晚迁」不是技术债陷阱，
   而是一个有明确撤离路径的选项。

## 为什么迁移成本可控

这是本决策成立的关键前提。架构 §8.2 强制两条约束：

| 约束 | 强制手段 | 实测结果 |
|---|---|---|
| `glasshouse-core` 零 Spring 依赖 | `maven-enforcer` 的 `bannedDependencies` | **68 个文件，0 个 Spring 引用** |
| Spring 依赖集中在 starter 一层 | 依赖方向 `cli → eval → starter → core` 单向 | **starter 内 7 个文件** |

因此迁 Boot 4.1 的改动面是：

- `glasshouse-core`（68 个文件）：**0 处改动** —— 它只依赖 OTel SDK、Jackson、SnakeYAML、picocli
- `glasshouse-spring-boot-starter`（7 个文件）：改动集中于此，主要是
  `ChatModelDecoratorBeanPostProcessor` 的注册方式与自动配置属性绑定
- 业务代码：**0 处改动** —— 这是「零代码侵入」这个卖点的直接推论

这 15 个文件（7 + 8 个 pom/配置）就是迁移的全部成本。

**两条约束都由构建强制，不靠 review 自觉**：
`maven-enforcer` 在 `core` 里出现 Spring 依赖会直接让构建失败，
所以「core 保持框架无关」不是一个可以随时间腐化的承诺。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 3.5 出现 CVE 但无 OSS 修复 | 商业支持至 2032-06-30（付费）；或按上面的路径自行迁 4.1 |
| 3.5.16 之后无新 patch，CI 因依赖解析漂移失败 | `pom.xml` **精确锁定 `3.5.16`**，不用 `3.5.x` 浮动版本 |
| 长期不迁移导致生态脱节 | 已在 README「已知限制」如实披露日期与商业支持窗口，不隐瞒 |

## 复查触发条件

出现以下任一情况时**重新评估**本决策：

1. Spring AI 官方发布稳定支持 Boot 4.x 的版本
2. Boot 3.5 出现高危 CVE 且商业支持采购受阻
3. 商业支持窗口剩余不足 12 个月（当前剩约 5 年 9 个月）

## 后果

- **负面**：首版用户继承 3.5 的 OSS 停更状态，必须自行决定是否购买商业支持
- **正面**：交付时间不必被「等生态就绪」阻塞；core 层的框架无关性已由构建强制，
  任何时候发起迁移都是 15 个文件的确定性工作，而不是重构

## 替代方案（已否决）

| 方案 | 否决理由 |
|---|---|
| 直接用 Boot 4.0 | OSS 支持也只剩 3 个月；Spring AI 兼容矩阵未定 |
| 等待 3.x 后续版本 | 3.5 是 3.x 末版，不存在 |
| 跟随 ①仓库（llm-switchyard）的 Boot 版本 | ①同样锁 3.5（其 README 已写明 2026-06-30）。三仓同一条 Boot 线可减少版本组合爆炸 |
